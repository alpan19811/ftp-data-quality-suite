FTP Data Quality Suite

Автоматизированный фреймворк проверок качества данных для банковской витрины расчёта трансфертных ставок (FTP). Проект моделирует типовой поток данных source → DWH → mart и реализует комплексные проверки Data Quality на стеке Python, pytest, psycopg2, pandas, NumPy, PostgreSQL.
Disclaimer: Реальные банковские данные (трансфертные ставки, стоимость фондирования, компенсации) защищены коммерческой тайной. Этот проект воспроизводит ту же методологию и инструментарий на синтетической модели — демонстрируя, как я подхожу к тестированию качества данных в банковских проектах.

Бизнес-контекст
Банки используют Funds Transfer Pricing (FTP) для распределения стоимости фондирования между бизнес-подразделениями. Для каждого кредитного договора типовая витрина FTP рассчитывает:
 - Итоговую трансфертную ставку = базовая ставка FTP + премия за ликвидность + компенсация резервов + компенсация опциона досрочного погашения
 - Маржу клиента = клиентская ставка − итоговая трансфертная ставка
 - Годовые суммы: FTP-плата, процент клиента, маржа в деньгах
Корректность этих расчётов напрямую влияет на отчётность о прибыльности, KPI филиалов и регуляторные показатели (LCR, NSFR). Проверки качества данных должны ловить не только форматы полей, но и нарушения бизнес-логики — например, отрицательная маржа означает, что банк теряет деньги на таком договоре.

Архитектура проекта
Проект реализует классическую трёхслойную архитектуру хранилища данных:
Слой source — сырые операционные данные (как они выгружаются из АБС и казначейства). Могут содержать дубли, аномалии и пропуски. Содержит таблицы: clients, contracts, treasury_ftp_rates.
Слой dwh — очищенное корпоративное хранилище. Справочники используют методологию SCD Type 2 (хранение истории изменений), факты дедуплицированы оконными функциями. Содержит таблицы: dim_client_scd2, fact_contract.
Слой mart — финальная аналитическая витрина данных. Денормализована для отчётности и проверок качества. Содержит итоговую таблицу ftp_contract_mart.
Слой dq — служебная схема для хранения результатов проверок качества данных. Содержит журнал dq_check_results.

Проверки качества данных (7 категорий, 16 тестов)
Фреймворк покрывает все классические измерения качества данных (Data Quality Dimensions):
1. Completeness (Полнота) — файл test_01_completeness.py. Проверяет отсутствие NULL в критичных полях витрины: contract_id, client_id, amount, client_rate, total_transfer_rate и др.
2. Uniqueness (Уникальность) — файл test_02_uniqueness.py. Проверяет уникальность бизнес-ключа (contract_id, report_date) — каждая комбинация должна встречаться только один раз.
3. Referential Integrity (Ссылочная целостность) — файл test_03_referential_integrity.py. Проверяет, что каждый клиент в витрине реально существует в справочнике dwh.dim_client_scd2. Ловит «клиентов-сирот».
4. Validity (Валидность) — файл test_04_validity.py. Четыре теста: суммы кредитов строго положительные, клиентская ставка в диапазоне (0; 1), итоговая трансфертная ставка положительная, маржа клиента неотрицательная.
5. Accuracy (Точность расчётов) — файл test_05_calculation_accuracy.py. Пять тестов, которые независимо пересчитывают производные показатели витрины через pandas и NumPy, сравнивая с фактическими значениями через np.isclose с допуском. Проверяются формулы: итоговой трансфертной ставки, маржи клиента, годовой FTP-платы, годового процента клиента, годовой маржи в деньгах.
6. Consistency (Консистентность между слоями) — файл test_06_reconciliation.py. Сверка количества строк и суммы кредитов между dwh.fact_contract и mart.ftp_contract_mart — ни один договор и ни один рубль не должны потеряться при построении витрины. Для денежных значений используется тип Decimal с точностью до копейки (правильный подход для финансовых систем).
7. Timeliness (Своевременность) — файл test_07_timeliness.py. Проверяет, что report_date в витрине не старше 7 дней от текущей даты, а у каждой строки проставлен технический атрибут load_dttm.

Почему это важно для банковской Data Quality
Тесты выходят за рамки проверки форматов. Например, тест на неотрицательность маржи ловит бизнес-дефекты: отрицательная маржа означает, что клиентская ставка ниже стоимости фондирования банка — банк теряет деньги на таком договоре. Именно такие проверки нужны инженеру качества данных в казначействе и FTP.

Драйвер БД: psycopg2-binary
Анализ данных: pandas, NumPy

База данных: PostgreSQL 16 (в Docker)
CI/CD: GitHub Actions
Контейнеризация: Docker, docker-compose

Как запустить
1. Клонировать репозиторий и подготовить окружение:
git clone <repository-url>
cd ftp-data-quality-suite
python -m venv .venv
source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt

2. Скопировать файл настроек (при необходимости изменить параметры подключения):
cp .env.example .env

3. Запустить базу данных:
docker compose up -d

При первом запуске контейнер автоматически выполнит все SQL-скрипты из папки sql/ в алфавитном порядке: создаст схемы (source, dwh, mart, dq), таблицы с ограничениями и комментариями, наполнит тестовыми данными (с намеренными дефектами для проверок качества), построит слой DWH (дедупликация через ROW_NUMBER(), фильтрация аномалий) и витрину (расчёты FTP с CTE и оконными функциями).

4. Запустить тесты:
pytest -v

Ожидаемый результат: 16 passed in ~0.3s.

5. Опционально — сформировать Allure-отчёт:
pytest --alluredir=allure-results
allure serve allure-results

SQL-паттерны, которые используются
Дедупликация через оконную функцию (в 04_build_dwh.sql):

ROW_NUMBER() OVER (
    PARTITION BY contract_id
    ORDER BY load_dttm DESC
) AS rn

Стандартный паттерн для сохранения самой свежей версии записи при устранении дублей.
Подбор актуальной ставки на дату (в 05_build_mart.sql):

ROW_NUMBER() OVER (
    PARTITION BY fc.contract_id
    ORDER BY r.valid_from DESC
) AS rn


Point-in-time lookup: выбор ставки казначейства, которая действовала на дату начала договора. Если ставок несколько — берём самую свежую.
Совместимость с Greenplum и Oracle
Проект основан на PostgreSQL, что даёт прямую совместимость с:
 - Greenplum — MPP-СУБД на базе PostgreSQL. Весь SQL-код совместим с Greenplum; для больших объёмов данных добавляются проверки по ключу распределения (distribution key) и перекосу данных (анализ количества строк по сегментам через gp_segment_id).
 - Oracle — требует минимальных правок диалекта (MINUS вместо EXCEPT, NVL/COALESCE, ROWNUM вместо LIMIT). Подключение через oracledb или cx_Oracle выполняется по той же схеме, что и psycopg2 в модуле src/db.py.
